The messaging surface is how you send WhatsApp from your own backend: one-off messages, Meta-approved templates, and bulk broadcasts, plus the templates and channels that back them.

## Scopes

| Scope | Grants |
|---|---|
| `messages:send` | Send a single message — text, template, media, interactive. |
| `messages:bulk` | [Launch broadcasts](/dev/endpoints/messages-bulk) and [read their status](/dev/endpoints/messages-bulk-status). |
| `templates:read` | [Read the approved template catalog](/dev/endpoints/templates-list). |
| `templates:create` | [Create templates](/dev/endpoints/templates-create) and submit them to Meta. |
| `templates:update` | [Edit an existing template](/dev/endpoints/templates-update). |
| `channels:read` | [List channels](/dev/endpoints/channels-list) and [WhatsApp numbers](/dev/endpoints/whatsapp-numbers). |
| `channels:connect` | [Start and poll a connect session](/dev/endpoints/channels-whatsapp-connect). |

`messages:send` and `messages:bulk` are deliberately separate: bulk is the higher-risk one, since it costs money at Meta and can damage sender reputation. Keep it in a key the marketing tool owns, not the one your transactional backend uses.

## The sending identity is `phone_number_id`

Every send takes a `phone_number_id`: the **numeric identifier Meta issues** for the sending number, like `109876543210987`. It is not a Keebai `ObjectId`, and it is not the phone number itself.

List the ones available to you with [`GET /v1/whatsapp/numbers`](/dev/endpoints/whatsapp-numbers) and cache the result — numbers change when someone connects or disconnects a channel, which is a human-timescale event, not a per-request one.

## The 24-hour window

WhatsApp only allows **free-form** messages inside 24 hours of the recipient's last inbound message. Outside that window Meta rejects the send.

| Situation | What to send |
|---|---|
| The user wrote to you in the last 24h | Anything — [text](/dev/endpoints/messages-text), media, interactive. |
| The window is closed, or they never wrote | A [Meta-approved template](/dev/endpoints/messages-template). |

<Warning>
  Keebai does **not** reject a free-form send when the window is closed. The request is accepted, forwarded to Meta, and the resulting broadcast ends in `FAILED`. A `202` means "queued", never "delivered" — check the outcome with [`GET /v1/messages/bulk/:broadcastId`](/dev/endpoints/messages-bulk-status) or an [outbound webhook](/dev/webhooks/overview).
</Warning>

## Every send is a broadcast

Single sends and bulk sends share one machine. A single send creates a broadcast with exactly one recipient, which is why both return the same envelope:

```json
{
  "broadcast_id": "65f4b5c6d7e8f9a0b1c2d3e4",
  "status": "PENDING",
  "total_recipients": 1,
  "scheduled_at": null
}
```

Keep the `broadcast_id`. It is the only handle you have for asking what happened afterwards.

This also makes the cost model clear: one broadcast to 5,000 recipients is **one** request against your [daily quota](/dev/rate-limits); a loop over 5,000 single sends is 5,000.

## Errors

```json
{
  "error": {
    "code": "THROTTLED",
    "message": "Rate limit exceeded: 1000 requests per day per token. Quota resets in 7h 12m."
  }
}
```

| Status | When |
|---|---|
| `400` | Invalid body, bad phone format, or a property the endpoint does not accept. |
| `401` | Missing, invalid, revoked, or expired token. |
| `403` | The token lacks the scope the endpoint requires. |
| `429` | You hit a [rate limit](/dev/rate-limits). |

Branch on `error.code`, not on the message text.
