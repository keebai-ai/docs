Every tool below is exposed by [`POST /v1/mcp`](/dev/mcp/overview) and delegates to the same service as its REST counterpart, so the behaviour, validation, and tenancy rules documented across these pages apply unchanged.

The **Scope** column is the scope your token needs. Without it the tool still appears in `tools/list`, and the call fails with `INSUFFICIENT_SCOPE` — see [how scopes are enforced](/dev/mcp/overview#scopes-are-enforced-per-tool-not-per-connection).

Tools marked 🔴 delete data permanently.

## Contacts

Read and write the people on the other side of your channels. See the [Contacts endpoints](/dev/endpoints/contacts-list) for the full field reference.

| Tool | Scope | What it does |
|---|---|---|
| `keebai_contacts_list` | `contacts:read` | List contacts, most recently active first. The way to find a contact id before opening a CRM ticket. Never returns merged contacts or the `playground` channel. |
| `keebai_contact_get` | `contacts:read` | Get one contact by id, with custom fields and last-activity timestamps. |
| `keebai_contact_create` | `contacts:write` | Create a contact. `user_id` is the identifier inside the channel — on WhatsApp, the phone without the leading `+`. |
| `keebai_contact_update` | `contacts:write` | Partial update. An empty string does not clear a field, and `custom_fields` is merged rather than replaced. |
| 🔴 `keebai_contact_delete` | `contacts:delete` | Delete a contact and its change history. Conversations survive. |

## CRM

The full pipeline: customers, tickets, tasks, notes. See the [CRM overview](/dev/crm/overview) for how the entities relate.

<Warning>
  CRM reads are **company-wide**. Every `*_list` and `*_get` tool returns records from every project in your company, not just the one the token was minted for.
</Warning>

| `keebai_send_contacts` | `messages:send` | Share contact cards in a chat. Does **not** create contacts — that is `keebai_contact_create`. |
| `keebai_send_reaction` | `messages:send` | React with an emoji; an empty emoji clears it. |
| `keebai_mark_read` | `messages:send` | Mark an inbound message read, optionally with the typing indicator. |
| `keebai_send_interactive_buttons` | `messages:send` | Up to 3 quick reply buttons. |

| `keebai_send_bulk` | `messages:bulk` | Broadcast a template to up to 5000 recipients. Costs money at Meta. |

## Ecommerce

The catalog, carts, and sales, plus stock, sale creation, and electronic invoicing (DTE). See the [ecommerce overview](/dev/ecommerce/overview) for how the records relate — a cart is not a draft sale.

| Tool | Scope | What it does |
|---|---|---|
| `keebai_ecommerce_products_list` | `ecommerce:products:read` | List the catalog with full-text search. Covers products created in Keebai and those synced from an integration. |
| `keebai_ecommerce_product_get` | `ecommerce:products:read` | Get one product with its variants, images, and stock. |
| `keebai_ecommerce_carts_list` | `ecommerce:carts:read` | List carts, including abandoned ones. Filter by recovery status to find the ones worth following up on. |
| `keebai_ecommerce_cart_get` | `ecommerce:carts:read` | Get one cart with its line items and the customer's contact details. |
| `keebai_ecommerce_sales_list` | `ecommerce:sales:read` | List sales by status, payment status, contact, or date range. |
| `keebai_ecommerce_sale_get` | `ecommerce:sales:read` | Get one sale with its items, amount breakdown, and payment state. |
| `keebai_ecommerce_product_find` | `ecommerce:products:read` | Find a product or variant by exact SKU or barcode (`match: "exact"`), or by text (`match: "search"`). |
| `keebai_ecommerce_stock_get` | `ecommerce:stock:read` | Stock of a product per variant: master total, allocated to branches, left in the warehouse, and per branch. |
| `keebai_ecommerce_stock_movements_list` | `ecommerce:stock:read` | Stock movements filtered by date, type, branch, or text. |
| ⚠️ `keebai_ecommerce_stock_adjust` | `ecommerce:stock:write` | Add or remove stock in the warehouse or a branch. Syncs to the connected stores. Not idempotent. |
| `keebai_ecommerce_stock_transfer` | `ecommerce:stock:write` | Move stock between the warehouse and branches. The total does not change. |
| ⚠️ `keebai_ecommerce_sale_create` | `ecommerce:sales:write` | Record a sale or an internal consumption, and issue its DTE in the same call (`dte.document`: `receipt`, `exempt_receipt`, `invoice`, `exempt_invoice`; `dte.due_date` for a credit invoice). Lines are a product (`product_id`, `variant_id`), a `sku`, or a free line with its own `name`; each line takes `price` (VAT included) or `net_price` (exact net). For an invoice, a known customer RUT fills in the rest of the receiver. `branch_id` defaults to the only active branch, and a single payment without `amount` charges the total. Missing data, payment or credit fails before anything is written. Pass `idempotency_key` to retry without duplicating. |
| ⚠️ `keebai_ecommerce_sale_payment_add` | `ecommerce:sales:write` | Record a payment received for a sale that is not fully paid, such as an invoice issued on credit. |
| `keebai_ecommerce_dte_types` | `ecommerce:invoicing:read` | The DTE documents the company can issue today, and whether it allows credit invoices. |
| ⚠️ `keebai_ecommerce_dte_issue` | `ecommerce:invoicing:issue` | Issue the DTE of an existing sale (`document`, `due_date` for a credit invoice). For an invoice, a known customer RUT fills in the rest of the receiver. Failures come back in `failed` with their reason. |
| `keebai_ecommerce_sale_documents` | `ecommerce:invoicing:read` | The DTE issued for a sale, with folio, status, and PDF link. |

<Warning>
  Tools marked ⚠️ have effects outside Keebai. A stock adjustment reaches the connected stores, a sale moves stock and money records, and a DTE is a document filed with the tax authority. None of them can be undone by calling the tool again.

  `ecommerce:stock:write` and `ecommerce:invoicing:issue` can only be put on a token whose owner has those permissions in their role (or is the company owner or a superuser) — see [scopes](/dev/scopes#scopes-are-independent-from-role-permissions). `keebai_ecommerce_sale_create` with a `dte` also needs `ecommerce:invoicing:issue`.

  The DTE PDF has no tool — it is a file, not JSON. Use [`GET /v1/ecommerce/invoicing/documents/{id}/pdf`](/dev/endpoints/ecommerce-invoicing-document-pdf).
</Warning>

## Loyalty

Points, stamps, and wallet cards. See the [loyalty overview](/dev/loyalty/overview) for the data model — in particular that there is no reward entity and that balances are a projection, not a sum of the ledger.

| Tool | Scope | What it does |
|---|---|---|
| `keebai_loyalty_programs_list` | `loyalty:read` | List programs, newest first. Only the rules variant matching the program's type is populated. Start here for the program id. |
| `keebai_loyalty_program_get` | `loyalty:read` | Get one program: points per currency unit and expiry, stamps target and reward, or tier thresholds. |
| `keebai_loyalty_templates_list` | `loyalty:read` | List a program's wallet card designs. Read-only — the card is designed in the portal. |
| `keebai_loyalty_template_get` | `loyalty:read` | Get one template with its branding, fields, and barcode. |
| `keebai_loyalty_memberships_list` | `loyalty:read` | Find a membership by customer id, phone, name, program, or status. Phone matches on a digit subsequence. |
| `keebai_loyalty_membership_get` | `loyalty:read` | Get one membership with its balance, stamps, and tier. |
| `keebai_loyalty_membership_enroll` | `loyalty:write` | Enroll a customer. The details are copied as given and never re-resolved; a repeat enrollment conflicts rather than duplicating. |
| `keebai_loyalty_ledger_list` | `loyalty:read` | Movement history of a membership, newest first, each entry with the balance it produced. |
| ⚠️ `keebai_loyalty_ledger_record` | `loyalty:write` | Move a balance — earn, redeem, or adjust. Updates the card in the customer's wallet. Not idempotent. |
| `keebai_loyalty_pass_issue_google` | `loyalty:write` | Issue the Google Wallet pass and return the save link. Reissuing reuses the existing pass. |
| `keebai_loyalty_pass_issue_apple_link` | `loyalty:write` | Issue the Apple Wallet pass and return a public download link. |
| ⚠️ `keebai_loyalty_pass_notify` | `loyalty:write` | Push a message to the customer's phone. A real notification to a real person. |
| `keebai_loyalty_pass_notifications_list` | `loyalty:read` | What was already sent to this membership, and how many devices it reached. |

<Warning>
  Tools marked ⚠️ have effects outside Keebai. `keebai_loyalty_ledger_record` moves a balance a customer can spend and is **not idempotent** — a retried call double-counts. `keebai_loyalty_pass_notify` sends a push notification to a real phone.

  Neither is destructive, so neither carries the 🔴 marker, but hand `loyalty:write` to an agent with the same care you would give `messages:send`.
</Warning>

## Scheduling

Branches, services, professionals, availability, and appointments. See the [scheduling overview](/dev/scheduling/overview) for the booking model — in particular that an appointment lands in `pending`, and that reading a slot does not hold it.

| Tool | Scope | What it does |
|---|---|---|
| `keebai_scheduling_branches_list` | `scheduling:branches:read` | List the active branches, each with its timezone. Start here for the branch id. |
| `keebai_scheduling_branch_get` | `scheduling:branches:read` | One branch with its address, contact details, and timezone. |
| `keebai_scheduling_services_list` | `scheduling:services:read` | List services with duration and price, filtered by branch, status, or name. Every availability query needs a service id from here. |
| `keebai_scheduling_service_get` | `scheduling:services:read` | One service with its duration, slot interval, price, and branches. |
| `keebai_scheduling_professionals_list` | `scheduling:professionals:read` | List professionals, filtered by branch, service, status, or name. |
| `keebai_scheduling_professional_get` | `scheduling:professionals:read` | One professional with specialties and branches. |
| `keebai_scheduling_availability_by_date` | `scheduling:availability:read` | Free slots for a service on one day, grouped by professional. |
| `keebai_scheduling_availability_range` | `scheduling:availability:read` | Free slots day by day between `from` and `to`, at most 14 days. |
| `keebai_scheduling_availability_next` | `scheduling:availability:read` | The soonest free slots for a service, up to `limit` per professional. |
| `keebai_scheduling_appointment_get` | `scheduling:appointments:read` | One appointment by id. |
| ⚠️ `keebai_scheduling_appointment_create` | `scheduling:appointments:create` | Book a slot with the customer embedded. Lands in `pending`, and already occupies the slot. |
| ⚠️ `keebai_scheduling_appointment_confirm` | `scheduling:appointments:confirm` | Move a `pending` appointment to `confirmed`. Any other state fails. |
| ⚠️ `keebai_scheduling_appointment_cancel` | `scheduling:appointments:cancel` | Cancel and release the slot, with an optional reason. |

Arguments keep the REST names: the availability and list tools take `serviceId`, `branchId`, and `professionalId` like the query strings they mirror, while `keebai_scheduling_appointment_create` takes `branch_id`, `service_id`, and `start_time` like the request body. Dates are `YYYY-MM-DD` and times `HH:mm`, both in the branch's timezone. The appointment id is a UUID, not an ObjectId.

<Warning>
  Tools marked ⚠️ reach the customer. Creating, confirming, or cancelling fires the [scheduling webhooks](/dev/webhooks/events#scheduling), the CRM event on the contact's timeline, and the reminder and confirmation notifications the account has configured.

  A slot read from availability is a snapshot, not a hold. When `keebai_scheduling_appointment_create` fails because the slot was taken, the agent should query availability again and offer the new options rather than retry the same time. An appointment left in `pending` holds its slot until someone cancels it; nothing expires it.
</Warning>

## Meet

Meeting types, availability, and meetings of [Keebai Meet](/dev/meet/overview), the scheduler for sales meetings. See the overview for [how hosts are assigned](/dev/meet/overview#how-hosts-are-assigned) and the reminders that go out on their own.

| Tool | Scope | What it does |
|---|---|---|
| `keebai_meet_types_list` | `meet:types:read` | List the meeting types, active ones by default, with duration, location, hosts, and assignment. Start here for the type id. |
| `keebai_meet_availability` | `meet:availability:read` | Open slots of a type, by day in the company time zone, each with the host who would take it. |
| `keebai_meet_meetings_list` | `meet:meetings:read` | List meetings, upcoming by default, filtered by host, type, customer, text, or dates. |
| `keebai_meet_meeting_get` | `meet:meetings:read` | One meeting with its video link, status, and reminders. |
| ⚠️ `keebai_meet_meeting_create` | `meet:meetings:create` | Book a slot. Creates the calendar event with the video link, invites the customer and guests, and schedules the reminders. |
| ⚠️ `keebai_meet_meeting_reschedule` | `meet:meetings:reschedule` | Move a meeting to a new slot; the event and the reminders move with it. |
| ⚠️ `keebai_meet_meeting_cancel` | `meet:meetings:cancel` | Cancel a meeting, its calendar event, and its pending reminders. |

Arguments keep the REST names. `start` is an ISO 8601 instant with `Z` or an offset: pass the `start` of a slot from `keebai_meet_availability` unchanged. A meeting booked through MCP is recorded with `source: "public"` and the token owner as `created_by`, like one booked through REST.

<Warning>
  Tools marked ⚠️ reach people outside Keebai: the customer and the guests get the calendar invitation, its update, or its cancellation, and the reminders by WhatsApp or email.

  A slot read from availability is a snapshot, not a hold. When `keebai_meet_meeting_create` fails with `SLOT_NOT_AVAILABLE`, the agent should query availability again and offer the new options rather than retry the same time.
</Warning>

| `keebai_agent_scenario_create` | `agents:write` | Add a scenario. An `instructions` one starts empty. Up to 50 per agent. |
| `keebai_agent_scenario_template_apply` | `agents:write` | Add a scenario from a template with all its routes, or nothing. An `information` template needs `knowledge_node_id`. Returns `missing_functions`. |
| `keebai_agent_scenario_update` | `agents:write` | Partial update. `knowledge_node_id: null` removes the folder. |
| 🔴 `keebai_agent_scenario_delete` | `agents:write` | Delete a scenario with its routes and their history. |
| `keebai_agent_route_create` | `agents:write` | Add a route: when it applies, steps up to 6 levels deep, cases. Mounts the functions it names. |
| `keebai_agent_route_update` | `agents:write` | Partial update. Writes a new version; `move_to_scenario_id` moves it. |
| 🔴 `keebai_agent_route_delete` | `agents:write` | Delete a route with its history. Archiving keeps it instead. |
| `keebai_agent_route_versions_list` | `agents:read` | The history of a route, newest first. |
| `keebai_agent_route_version_restore` | `agents:write` | Restore a version by writing a new one that copies it. |
| `keebai_agent_tests_list` | `agents:read` | The saved tests of an agent, each with the verdict of its latest run, plus a summary by verdict and the run in progress. |
| `keebai_agent_test_save` | `agents:write` | Create a test, or update one when `test_id` is sent. `expected_tools` lists the functions the agent has to call for an attempt to pass. `status: archived` takes it out of the runs; a test is never deleted. |
| `keebai_agent_tests_run` | `agents:write` | Start a run and return at once. Each test is talked through 3 times in test mode. Fails with `run_in_progress` while one is going. |
| `keebai_agent_test_run_get` | `agents:read` | One run with every attempt: conversation, functions used (simulated ones marked) and why it passed. Without `run_id`, the latest runs. |

<Warning>
  **Writing here changes what your bots say to customers.** An agent with `agents:write` can rewrite any prompt section and create webhook tools that make Keebai's infrastructure call an external host — the URL is validated against loopback, private ranges and internal names, but a public host of the agent's choosing is allowed. Treat it as a higher-privilege scope than the read side, and read [webhook security](/dev/agents/webhook-security) before handing it out.

  **Tools are company-wide**, unlike agents and their sections, which are scoped to the token's project.

  **`keebai_agent_query` never touches real data.** It runs the turn with the write tools simulated, so an agent can verify its own change without booking anything.

  **Test runs cost conversations.** `keebai_agent_tests_run` holds 3 simulated conversations per test, each reviewed against its `pass_if`. They run in test mode with an invented customer, so nothing is booked or written, but every conversation runs the agent, the simulated customer and the review on the model.
</Warning>

## Not exposed as tools

WhatsApp templates, channels, webhooks, tenants, and setup links have no MCP tools yet. Use the [REST API](/dev/overview) for those.

[CRM events](/dev/crm/events) are not tools either, and that one is on purpose rather than pending. Emitting an event is a system-of-record write from a system that *knows* something happened — an order closed, a delivery completed. A model deciding to emit one is a model asserting a fact it cannot verify. Call [`POST /v1/webhook/events`](/dev/endpoints/crm-events-emit) from the system that owns the fact.

<Note>
  Keebai's own agents *can* emit events, through an internal tool gated by an `ai_triggerable` flag you set per event type in the portal. That flag defaults to off and does not apply to this MCP server, which is your agent talking to the API, not Keebai's agent talking to itself.
</Note>

The binary Apple `.pkpass` has no tool either, for the same reason as media download: it is a file, not JSON. The Apple link tool covers the same use case.
