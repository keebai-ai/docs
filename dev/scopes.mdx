Every Personal Access Token (PAT) carries a set of **scopes** — the list of actions that token can perform against the public API. You pick scopes at creation time, and they're immutable afterward — to change them, mint a new token and revoke the old one.

## How they're validated

On every request, the auth guard loads the token and puts its scopes on the request context. Each endpoint declares the scope it needs with `@RequireScopes('messages:send')`. If the scope is missing, the response is `403 Forbidden` with `code: INSUFFICIENT_SCOPE`.

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json
```

```json
{
  "error": {
    "code": "INSUFFICIENT_SCOPE",
    "message": "Forbidden",
    "details": {
      "required": ["messages:bulk"],
      "missing": ["messages:bulk"]
    }
  }
}
```

Unlike auth errors (which are intentionally generic), authorization errors spell out which scope is missing — because you already authenticated successfully; you just lack permission.

## The MCP server uses the same scopes

The [MCP server](/dev/mcp/overview) does not have a scope system of its own. Each of its tools requires exactly the scope its REST counterpart does — `keebai_crm_ticket_create` needs `crm:tickets:write`, `keebai_contacts_list` needs `contacts:read`, and so on. The [tool catalogue](/dev/mcp/tools) lists the mapping.

One difference matters when you hand a token to an agent: **a missing scope is not a `403`**. Every tool stays visible in `tools/list` regardless of your scopes, and the call comes back as a tool error carrying `INSUFFICIENT_SCOPE`. An agent will happily try something it cannot do and discover the limit afterwards, so pick the scope set deliberately rather than relying on the agent not to reach for a tool.

## Permission groups

When an app connects to the [MCP server over OAuth](/dev/mcp/overview#connect-with-oauth) — Claude, ChatGPT, Cursor — the user does not tick scopes one by one. The consent screen shows six **groups**. The token ends up with the scopes the app asked for that belong to a group the user approved and that the user's role allows.

Each scope's group is stored with it in the `api_scopes` catalog, as `consent_group`. It is not derived from the scope's name: `contacts:` and `loyalty:` sit with `crm:` in **Customers**, `restaurants:menu:read` sits with the catalog reads in **Products and sales**, and `ecommerce:` splits by action — reads go to **Products and sales**, anything that writes or issues goes to **Sell and invoice** — so a user can let an app look at sales without letting it create them.

| Group | Key | Scopes |
|---|---|---|
| **Messages and email** | `messages` | `messages:send`, `messages:bulk`, `templates:read`, `templates:create`, `templates:update`, `channels:read`, `channels:connect`, `webhooks:read`, `webhooks:manage`, `flows:read`, `flows:write` |
| **Customers** | `customers` | `crm:customers:read`, `crm:customers:write`, `crm:customers:delete`, `crm:tickets:read`, `crm:tickets:write`, `crm:tickets:delete`, `crm:tasks:read`, `crm:tasks:write`, `crm:tasks:delete`, `crm:notes:read`, `crm:notes:write`, `crm:notes:delete`, `crm:events:write`, `contacts:read`, `contacts:write`, `contacts:delete`, `loyalty:read`, `loyalty:write` |
| **Calendar** | `scheduling` | `scheduling:branches:read`, `scheduling:sectors:read`, `scheduling:services:read`, `scheduling:professionals:read`, `scheduling:availability:read`, `scheduling:appointments:read`, `scheduling:appointments:create`, `scheduling:appointments:update`, `scheduling:appointments:confirm`, `scheduling:appointments:cancel`, `scheduling:payment-links:create` |
| **Products and sales** | `catalog` | `restaurants:menu:read`, `ecommerce:products:read`, `ecommerce:carts:read`, `ecommerce:sales:read`, `ecommerce:stock:read`, `ecommerce:invoicing:read` |
| **Sell and invoice** | `commerce` | `ecommerce:carts:write`, `ecommerce:sales:write`, `ecommerce:stock:write`, `ecommerce:invoicing:issue` |
| **Agents and knowledge** | `agents` | `knowledge:read`, `knowledge:write`, `knowledge:delete`, `knowledge:query`, `knowledge:assign`, `agents:read`, `agents:write`, `projects:read` |

`cli:device` is in no group. It is an internal marker that Keebai puts on tokens issued to the [CLI](/dev/sdks/cli), not a permission an app can ask for. Inactive scopes are in no group either.

Rules that apply on the consent screen:

- **Your role limits the groups.** A group is available only if your Keebai role has the permission behind at least one of the scopes the app asked for in it. Inside an approved group, scopes your role does not allow are left out. The company owner and superusers can approve every group.
- **One company per connection.** The user picks the company before approving. To use another company, connect again.
- **Reconnecting replaces.** A second approval from the same user, for the same app and company, replaces the scopes of the first one.
- **Disconnecting stops the connection within 15 minutes.** Under **Developers › Connected apps** in the portal, the company owner and superusers see every connection in the company and everyone else sees their own. Disconnecting revokes the refresh token at once; the app's current access token is not revoked and expires on its own, at most 15 minutes later.
- **Losing access ends the connection.** If the user is deactivated or loses access to the company, the app's next refresh fails and it has to sign in again. A change of role alone does not change the scopes already granted; disconnect and connect again to apply it.

Personal Access Tokens do not use groups. You still pick single scopes when you [create a token](/dev/api-keys).

## Scopes are independent from role permissions

Scopes are **independent** from the role permissions of the user who creates the token. The backend validates *what scopes you're allowed to assign* at creation time (each scope must exist and be active in `api_scopes`, and a few are tied to role permissions — see below), but once minted, the token uses its assigned scopes regardless of later changes to your role.

That means:

1. **To create a token** you need `developer.manage_tokens` on your role. Without it you don't even see the API Keys screen.
2. **Once created, a token's scopes are fixed.** If your role is later trimmed, the token keeps working with its original scopes. To revoke access, revoke the key explicitly.
3. **To use new scopes, mint a new token.** You can't add scopes to an existing key.

<Note>
  **Two ecommerce scopes require the permission in your role.** Minting a token with `ecommerce:stock:write` requires the permissions to adjust and transfer stock in your Keebai role, and `ecommerce:invoicing:issue` requires the permission to issue DTE. The company owner and superusers are exempt. On every call the API passes the ecommerce service the permissions that match the token's scopes, so what the token can do is what the role allowed when it was minted.
</Note>

<Warning>
  Because scopes survive role changes, **audit the API Keys table periodically** and revoke tokens belonging to people who shouldn't have access anymore. The *Last used* column helps find forgotten keys.
</Warning>

## Change a token's scopes

You can't edit scopes on an existing token. The pattern is:

<Steps>
  <Step title="Mint a new token with the right scopes">
    From [API Keys](https://app.keebai.com/system-settings/api-keys), click **Create API Key** and pick the new scopes.
  </Step>
  <Step title="Update your integration">
    Swap the old token for the new one in your secret manager.
  </Step>
  <Step title="Revoke the old">
    Once the integration is happily on the new token, revoke the old one.
  </Step>
</Steps>

This pattern gives you zero-downtime rotation.
